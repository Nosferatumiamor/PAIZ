# Ce que je demanderais à Cursor

Je lui donnerais un prompt énorme.

Pas juste :

> Fais un projet.

Mais quelque chose comme :

---

> Nous développons un moteur C++17 nommé **WeightStream**.
>
> Ce projet n'est PAS un moteur d'inférence.
>
> Son rôle est uniquement de streamer des blocs de poids entre SSD, RAM et VRAM afin d'alimenter un GPU sans interruption.
>
> Le moteur doit être conçu comme un moteur de streaming d'assets de jeu vidéo (textures, meshes...) appliqué aux poids d'un réseau neuronal.
>
> Les objectifs sont :
>
> * architecture modulaire
> * CMake
> * classes courtes
> * multithreading
> * préfetch asynchrone
> * cache RAM
> * cache VRAM
> * scheduler
> * métriques
> * logs
> * aucun code spécifique aux LLM dans un premier temps
>
> Les blocs représentent des tenseurs.
>
> Ils possèdent :
>
> * id
> * taille
> * offset disque
>
> Le moteur doit simplement être capable de demander :
>
> ```cpp
> auto tensor = cache.GetTensor(id);
> ```
>
> sans savoir où il est physiquement.
>
> Toute la logique de streaming est cachée.
>
> Le code doit être documenté, propre et facilement extensible vers GGUF.

## Ce que j'ajouterais

J'essaierais de convaincre Cursor de **ne pas penser "LLM" mais "Unreal Engine"**.

Parce qu'en réalité, ce qu'on construit est une sorte de **Virtual Memory Manager**.

Et là, j'ai une idée qui pourrait être vraiment originale.

Au lieu de streamer des **layers**, on pourrait streamer des **tensors individuels**.

Les moteurs actuels raisonnent souvent en couches complètes, alors qu'un fichier GGUF est déjà organisé en dizaines ou centaines de tenseurs (matrices de projection, embeddings, etc.). Si certains tenseurs sont beaucoup plus volumineux ou beaucoup plus critiques que d'autres, un ordonnanceur intelligent pourrait optimiser encore davantage les transferts.

Je pense qu'avant d'écrire la moindre ligne de code, on devrait aussi faire un vrai document d'architecture (un mini-RFC de 15 à 30 pages) qui décrit les composants, les flux de données, les interfaces, les politiques de cache et les objectifs de performance. Avec un document solide, Cursor aura un cadre beaucoup plus précis et produira une base de code bien plus cohérente que s'il improvise. C'est exactement le genre de projet où une bonne architecture fait gagner énormément de temps ensuite.
